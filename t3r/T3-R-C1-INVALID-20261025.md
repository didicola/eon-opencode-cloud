## What was found

C1 ingested the public token `T3R-20261025T210513Z-ef98049f` at
`2026-10-25T21:05:16Z`; the immediate search hit it and the C1 evidence recorded
`knowledge 67→68`. That C1 artifact remains historical evidence of an isolated
write, but it is not a durable retention baseline.

At `21:40Z`, twelve repeated local reads showed the store is not stable:

- `brain_status.knowledge`: **64 × 9**, **68 × 3**
- exact-token `knowledge_search`: **1 hit / 12 reads**
- no transport errors

Direct reads of the durable edge-brain KV value (`brain-store`, namespace
`62085a396d954671a64e98cf436a7dd4`) at `21:43–21:44Z` returned **three identical
reads**:

- HTTP `200`, `32366 B`
- `know` entries: **64**
- C1 token hits: **0**
- sha256 `038032cb0ea68f1400246e1142485abf9f17ad332c6d3a2e46bfbd363021e2fd`

The token existed only in a few warm isolates' in-memory `KNOW` maps. It was
**not durable in the active KV lane**. The source has a D1 fallback write, but
it is not read when KV returns a store; that fallback was not verified here. A
24-hour C2 would therefore fail to retrieve the token, or would measure isolate
memory rather than retention.

## Root cause (corrected 2026-10-25T22:05Z)

**Measured immediate cause: account-wide KV write quota exhaustion.** A direct
Cloudflare KV `PUT` to the edge-brain namespace at `21:55Z` returned:

```
HTTP 429  code 10048
"your account has reached the free usage limit for this operation for today"
```

The edge-brain persists by `KV.put("brain-store", ...)` and catches write
failures silently. The C1 `brain_learn` therefore returned an in-memory success
(`68`) while the durable write failed. The later 1/12 token hits came from the
warm isolate that held the token in memory.

A post-patch fixture at `21:53Z` confirmed the same path: `/knowledge` returned
`size:65`, but KV remained **64** entries with **0** `brain-item:` keys. It was
not durable.

**Secondary design risk (not proven as this loss's cause):** live
`eon-edge-brain` hydrates `KNOW` once per isolate and persists the entire local
map. A stale isolate could overwrite a newer full map. The per-item patch below
removes that risk by writing immutable item keys, but the measured C1 loss is
quota-blocked persistence, not a proven stale overwrite.

## Remediation deployed

Owner approved the `eon-edge-brain` persistence patch and a new C1b baseline on
2026-10-25. The deployment is live:

- Per-item durable keys `brain-item:<key>` are written for changed knowledge
  entries. A stale full-map write can no longer erase an item.
- `brain-store` is still written for compatibility.
- A 5s hydrate TTL plus forced hydrate on `/status`, `/knowledge`,
  `/knowledge/search`, and `/knowledge/export` makes warm isolates see new
  item keys.
- Read-only `/kvcheck?q=<token>` reports `know`, `token_hits`, `items`, and
  `item_token_hits` from durable KV for pre-C2 validation.
- Unit test (two stale module instances + simulated full-map overwrite):
  **PASS**. The token survived a full-map overwrite and was recovered by both a
  stale and a fresh isolate.
- Deploy HTTP `200`; etag `972306e3dcd69401978f3f7d755e3d9a42915dc69b05592aa5e7310a3ddbc5bc`;
  bindings preserved: `D1_TOKEN`, `GEMINI_KEY`, `GROQ_KEY`, `KV`.
- Live `/health`, `/ping`, `/status`, `/knowledge/search` remain green.
- Live `/kvcheck` currently reports `know:64, items:0` because KV writes are
